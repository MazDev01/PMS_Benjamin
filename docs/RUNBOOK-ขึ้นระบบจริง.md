## ข. ขั้นตอนวันจริง

### 1 · ปิดปรับปรุง
- **คำสั่ง:** ไม่มีสวิตช์ปิดปรับปรุงในระบบ — "ปิด" = เริ่มตามเวลาที่แจ้งดีลเลอร์ไว้ (นอกเวลาทำการ) · ทีม HQ งดใช้ระบบ
  (ถ้าต้องการหน้า "ปิดปรับปรุง" จริงบนเว็บ ต้องสั่งผมทำเพิ่มล่วงหน้า — ยังไม่มี)
- **ผ่าน:** ถึงเวลาที่แจ้ง · ไม่มีใครในทีมกำลังใช้
- **ถ้าพัง:** — (ยังไม่มีการเปลี่ยนแปลงใด ๆ เลื่อนวันได้เลย)

### 2 · ลงใบแก้ฐานข้อมูล (สำรองอัตโนมัติก่อน)
- **คำสั่ง (บอสสั่ง → ผมรัน):**
  1. ดูก่อนไม่แตะฐาน: `npm run db:push:prod -- --yes-prod --dry-run`
  2. ลงจริง: `npm run db:push:prod -- --yes-prod`
- **ผ่าน:**
  - ข้อ 1 แสดงใบที่จะลง **0185 ถึง 0211 = 27 ใบ** ไม่มีใบอื่นปน (ระบบจริงลง 0182–0184 ไว้แล้ว · ตรวจ 15 ต.ค. 69: ตรงกับไฟล์ในโค้ดทุกชิ้น)
  - ข้อ 2: บรรทัดสำรองข้อมูลสำเร็จ (จดชื่อโฟลเดอร์สำรองไว้ — ใช้ในหมวด ค) → `Applying migration 0185…` ถึง `0211` → จบโดยไม่มี error → `🔓 ปลดการผูก CLI ออกจากฐานจริงแล้ว`
  - ตรวจซ้ำ: วาง `docs/prod-readonly-check.sql` ใน SQL Editor → `ใบล่าสุดบนระบบจริง` = **0211** · ผมตรวจส่วนสิทธิ์ต้อง **0 จุด**
- **ถ้าพัง:**
  - สำรองไม่สำเร็จ → สคริปต์หยุดเอง ยังไม่ลงอะไร → เลื่อนวัน แก้ที่เก็บสำรองก่อน
  - ใบใดล้มกลางทาง → **หยุด ห้าม push โค้ด** · ใบก่อนหน้าลงไปแล้ว ใบที่ล้มย้อนเองในตัว
    ส่งชื่อใบ + ข้อความ error ให้ผม → ตัดสิน: แก้แล้วลงต่อ / ย้อน (หมวด ค)
    ⚠️ ถ้าล้มหลังใบ 0203 แล้ว โค้ดเก่าบนเว็บจะ**ออกใบเสนอราคาไม่ได้** จนกว่าจะลงต่อสำเร็จหรือย้อน

### 3 · ลงโค้ด → รอ Vercel build เสร็จ
- **คำสั่ง (บอสสั่ง → ผมรัน):** `git push origin monorepo`
- **ผ่าน:**
  - Vercel → `benjamin-hq` และ `benjamin-dealer` → Deployments: รายการ Production ใหม่ **Ready** ทั้งคู่ · commit ตรงกับที่ push (~2–3 นาที/โปรเจกต์)
  - เปิด https://pms.benjaminpebsteel.com/api/health และ https://dealerpms.benjaminpebsteel.com/api/health → `"status":"ok"`
  - GitHub → Actions → "ตรวจเว็บจริงหลังอัปโค้ด" รันเองหลัง deploy → เขียว
- **ถ้าพัง:**
  - build ล้ม → Vercel คงรุ่นเก่าไว้ให้อัตโนมัติ (แต่รุ่นเก่า + ฐานใหม่ = ออกใบไม่ได้) → ส่ง log ให้ผม แก้แล้ว push ใหม่ / หรือย้อน (หมวด ค)
  - ล้มเพราะงานตั้งเวลา (`Hobby accounts are limited to daily cron jobs`) = ข้อ ก2 ยังไม่ครบ
  - health ไม่ ok → ดูว่าช่องไหน false (config/database) → ส่งผลให้ผม

### 4 · ตั้งอายุใบผ่าน 600–900 วินาที (บอสทำ)
- **คำสั่ง:** Supabase ระบบจริง → **Authentication** → หน้าตั้งค่า Sessions/JWT → **JWT expiry** = `900` (หรือ 600–900) → Save
  (ชื่อเมนูอาจเลื่อนตามรุ่นหน้าเว็บ — ค้นคำว่า "JWT expiry")
- **ผ่าน:** ค่าบันทึกแล้ว · ผู้ใช้เดิมไม่หลุด (ระบบต่ออายุใบผ่านเอง)
- **ถ้าพัง:** ตั้งกลับค่าเดิม (ค่าตั้งต้น 3600) — ไม่กระทบข้อมูล

### 4ก · เปิด Send Email Hook: Postgres · public · hook_send_email (บอสทำ · โค้ดทำให้ไม่ได้)
> 19 ต.ค. 69 ขั้นนี้หลุด: ลงใบ 0213 แล้วแต่ระบบจริงมีแค่ Customize Access Token hook → ฟังก์ชันปิดอีเมลไม่เคยถูกเรียก
> ลงใบอย่างเดียว = ยังไม่กันอะไร ลิงก์ลืมรหัสผ่าน/เลขเข้าระบบยังส่งไปโดเมนที่เราไม่ได้คุมได้
- **คำสั่ง:** Supabase ระบบจริง → **Authentication** → **Hooks** → **Send Email Hook** → ชนิด **Postgres** · schema **public** · ฟังก์ชัน **hook_send_email** → Save
  **ห้ามแตะ Customize Access Token hook** (ตัวนั้นใส่สิทธิ์ลง JWT — ปิด = ทุกคนเห็นข้อมูลว่าง)
- **ผ่าน:** หน้า Hooks มี 2 ตัวเปิดอยู่ (Customize Access Token + Send Email) · ชุด prod-live ข้อ "/recover และ /otp ถูก Send Email Hook ปฏิเสธ (403)" ผ่าน
  (ข้อนั้นตรวจ 403 + ข้อความ `auth_email_disabled` · ไม่มีบันทึกส่งลิงก์ · ล็อกอินรหัสผ่านยังได้ user_role/dealer_code ใน JWT)
- **ถ้าพัง:** ได้ 500 หรือ 200 = Hook ไม่ได้เปิด/ชี้ผิดตัว → กลับไปดูหน้า Hooks · ล็อกอินไม่ได้ = ปิด Send Email Hook ก่อน แล้วส่งผลให้ผม

### 5 · ทดสอบจริง 1 รอบ (บัญชีดีลเลอร์ทดสอบ + บัญชี HQ)
ใช้ชื่อลูกค้าเป้าหมาย **`ZZTEST-ขึ้นระบบ-<วันที่>`** และจังหวัดในพื้นที่ของดีลเลอร์ทดสอบ
1. ดีลเลอร์: เพิ่มลูกค้าเป้าหมาย → แท็บใบเสนอราคา → **ขอราคาจาก HQ** → **ผ่าน:** สถานะ "รอราคา HQ"
2. HQ: เมนู **คำขอใบเสนอราคา** → เปิดคำขอ → ทำ BOQ → **ส่งใบ HQ** → **ผ่าน:** ขึ้นว่าส่งแล้ว
3. ดีลเลอร์: เปิดลูกค้าเป้าหมายเดิม → **ทำใบเสนอราคาจากใบ HQ** → ใส่ % → สร้างใบ → **ผ่าน:** ใบลงรายการ · ราคาขาย = ต้นทุน × (1 + %)
   · งาน "จัดทำใบเสนอราคา" ติ๊กเอง · ไทม์ไลน์มี "ออกใบเสนอราคา …"
4. HQ: เปิดใบนั้น → เห็นต้นทุน · % · ส่วนบวกรายบรรทัด (ฝั่งดีลเลอร์/หน้าพิมพ์ต้องไม่มีต้นทุน)
5. ปิดงานทดสอบ: ดีลเลอร์ปิดลูกค้าเป้าหมายเป็น **ปิดการขายไม่สำเร็จ** เหตุผล "ทดสอบขึ้นระบบ" (ไม่นับเป็นยอดขาย)
- **ถ้าพัง:** จดขั้นที่พัง + ข้อความบนจอ → ส่งให้ผม · ระหว่างแก้ ระบบยังปิดปรับปรุงอยู่ · แก้ไม่ทันในช่วงปิดปรับปรุง → ย้อน (หมวด ค)

### 6 · ผ่าน → ตั้งเครื่องหมายรหัสชั่วคราว (ในช่วงปิดปรับปรุงเดียวกัน) → เปิดระบบ
- **คำสั่ง (บอสสั่ง → ผมรัน):**
  1. ดูจำนวนก่อน: `node scripts/flag-temp-passwords.mjs --prod`
  2. ตั้งจริง: `node scripts/flag-temp-passwords.mjs --prod --apply --yes-prod`
- **ผ่าน:** ข้อ 2 พิมพ์ `ตั้งเครื่องหมายแล้ว N บัญชี` โดย N = "ต้องตั้งเครื่องหมาย" ในข้อ 1 · สคริปต์ไม่พิมพ์อีเมล/รหัสสาขา
  · ผล: บัญชีเหล่านี้เข้าระบบครั้งถัดไปต้องตั้งรหัสใหม่ + ยืนยันอีเมลติดต่อก่อนเห็นข้อมูล
- **ถ้าพัง:** รันซ้ำได้ (ไม่ตั้งซ้ำ) · ตั้งผิดบัญชี → แจ้งผม (ถอดเครื่องหมายรายบัญชีได้ที่ Supabase → Authentication → Users → app_metadata)
- **เปิดระบบ:** แจ้งดีลเลอร์ว่าใช้งานได้แล้ว + วิธีใหม่: ขอราคาจาก HQ → รอใบ HQ → บวก % ทำใบให้ลูกค้า

### 7 · สวิตช์ซ่อนราคาแม่แบบ — ยกเลิกแล้ว (ไม่ต้องทำ)
- เอาแม่แบบออกทั้งระบบ 16 ต.ค. 69 → ไม่มีราคาแม่แบบให้ซ่อน · สวิตช์ปล่อยเป็น `false` ตามเดิม ไม่ต้องตรวจ ไม่ต้องเปิด (GO-LIVE-CHECKLIST §5.1)

2. SQL Editor ระบบจริง → วาง [ย้อนฉุกเฉิน-1-ปิดด่านให้โค้ดเก่า.sql](ย้อนฉุกเฉิน-1-ปิดด่านให้โค้ดเก่า.sql) → Run → ผลต้องเป็น `ด่านใบHQ = ปิด`
3. ทดสอบด้วยบัญชีดีลเลอร์: ล็อกอิน · ดูลีด · แก้ลีด · ออกใบแบบเดิม (ไม่ผ่านข้อไหน = หยุด ส่งข้อความ error ให้ผม)
4. แจ้งดีลเลอร์ว่ากลับมาใช้แบบเดิมชั่วคราว · คำขอราคา/ใบ HQ ที่ทำไว้แล้วยังอยู่ครบ แต่หน้าจอเก่าไม่แสดง
5. ส่งข้อความ error/ขั้นที่พังให้ผม → แก้ → ลงโค้ดใหม่
6. **ทันทีที่โค้ดใหม่ขึ้น:** วาง [ย้อนฉุกเฉิน-2-เปิดด่านคืน.sql](ย้อนฉุกเฉิน-2-เปิดด่านคืน.sql) → ผลต้องเป็น `ด่านใบHQ = เปิด` · ช่องจำนวนใบที่ไม่มีใบ HQ = ใบที่ออกระหว่างย้อน ให้ HQ ตามต่อ
