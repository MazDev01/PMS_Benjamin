# ทำงานหลายเซสชันพร้อมกัน

ทุกเซสชันทำงานพร้อมกันได้โดยไม่ชนกัน เพราะเครื่องมือเป็นตัวกัน ไม่ต้องบอกกันเองทางข้อความ
คนรวมงานมีคนเดียว ทำงานในโฟลเดอร์หลัก `C:\.claude\Benjamin-HQ-main` (ตอนนี้คือเซสชัน b4)

## 1. เปิดเซสชันใหม่ (บอสสั่งจากโฟลเดอร์หลัก)

```
npm run session:new -- <ชื่อ>
```

ชื่อเป็นภาษาอังกฤษตัวเล็ก เช่น `ef` หรือ `notify-th` แล้วเปิด Claude ใหม่ในโฟลเดอร์ที่คำสั่งบอก คำสั่งนี้เตรียมให้ครบ:

- โฟลเดอร์ `C:\.claude\pms-wt\<ชื่อ>` และ branch `session/<ชื่อ>` แยกจาก `wip/integration` ล่าสุด
- พอร์ตของเว็บที่ไม่ซ้ำเซสชันอื่น (เก็บใน `.pms-session.json`) ไฟล์ค่าตั้งเปลี่ยนพอร์ตให้แล้ว
- โปรแกรมเสริม (`node_modules`) ของโฟลเดอร์นั้นเอง

## 2. ทำงานในเซสชัน

- ทำงานในโฟลเดอร์ของตัวเองเท่านั้น
- commit ได้เฉพาะ `session/<ชื่อ>` · push ได้เฉพาะ `session/<ชื่อ>` (git hook ปฏิเสธ wip และ monorepo)
- ใบปรับฐานใหม่: `npm run migration:new -- <ชื่อใบ>` ได้เลขที่ไม่ซ้ำกับทุกเซสชันเสมอ ห้ามตั้งเลขเอง
- ฐานทดสอบมีชุดเดียว ทุกอย่างที่เขียนฐาน (ข้อทดสอบ · รอบตรวจเต็ม · ล้าง/ตั้งต้นฐาน) ถือล็อกฐานทดสอบอัตโนมัติ
  มีเซสชันอื่นใช้อยู่ → หยุดพร้อมบอกว่าเซสชันไหน เริ่มเมื่อไร (รอคิวแทน: `PMS_TESTDB_LOCK_WAIT=<นาที>`)
- **ฐานทดสอบเขียนได้เฉพาะผู้ถือล็อก (26 ต.ค. 69)** — ได้ล็อก = ได้กุญแจเขียนใหม่ทาง env ส่งต่อให้ตัวลูกทุกตัว · ปล่อยล็อก = กุญแจถูกสุ่มทิ้ง
  - `docker exec … psql -U postgres` ตรง ๆ เขียนไม่ได้แล้ว — สคริปต์ที่ต้องเขียนใช้ `อาร์กิวเมนต์psql(คอนเทนเนอร์)` จาก `scripts/lib/testDbGuard.mjs` หลังขอล็อก
  - อ่านอย่างเดียวไม่ต้องถือล็อก: `อาร์กิวเมนต์psql(คอนเทนเนอร์, { เขียน: false })` (บัญชี pms_reader)
  - ทาง API: ทุกคำขอเขียนต้องมีกุญแจของรอบ (หัวคำขอ `x-pms-lock`) ไม่ว่าจะใช้กุญแจ anon/service หรือล็อกอินเป็นผู้ใช้ — ไม่มี/ไม่ตรง = อ่านได้อย่างเดียว
    โปรแกรมของผู้ถือล็อกแนบให้เอง (`scripts/lib/testDbFetchKey.mjs`) · เว็บที่ชุดทดสอบเปิดแนบจากเบราว์เซอร์ (`NEXT_PUBLIC_PMS_TESTDB_LOCK`)
  - ข้อทดสอบ: `node tests/tools/testdb-guard.test.mjs` · พิสูจน์ว่าข้อทดสอบจับได้: `node tests/tools/testdb-guard-mutation.mjs`
  - **ข้อจำกัดที่รู้อยู่ (บอสรับแล้ว 26 ต.ค. 69):**
    1. คนที่ตั้งใจใช้สิทธิ์ root ของ docker แก้ไฟล์ในกล่องฐาน หรือตั้งใจเปิดอ่านไฟล์รหัสผู้ดูแล (`%USERPROFILE%\.pms-testdb-admin.json`) ข้ามการกันได้
    2. อัปโหลดไฟล์ (storage) และสร้างบัญชีผ่านระบบเข้าสู่ระบบ ไม่ผ่านตัวตรวจกุญแจ
    3. งานตามเวลา (pg_cron) ในฐานทดสอบไม่ทำงาน — ข้อทดสอบเรียกคำสั่งตรงอยู่แล้ว
- **ฐานทดสอบตรงกับไฟล์ใบปรับฐานของผู้ถือล็อกเสมอ (26 ต.ค. 69)** — ทุกครั้งที่ขอล็อก (รอบตรวจเต็ม · playwright · สคริปต์) เทียบโครงสร้างฐาน
  (ฟังก์ชัน · ตาราง/คอลัมน์ · ข้อบังคับ · ดัชนี · ตัวดัก · กฎรายแถว · ชนิดข้อมูล · สิทธิ์) กับลายของไฟล์ใบในโฟลเดอร์ของผู้ขอ
  - ไม่ตรง → บอกว่าอะไรไม่ตรง น่าจะมาจากเซสชันไหน แล้วสร้างฐานใหม่จากไฟล์ของผู้ขอก่อนรัน · สร้างไม่ได้ = ไม่ให้ล็อก (ไม่รันบนฐานที่ไม่ตรง)
  - ชุดใบใหม่ (เพิ่ม/แก้ไฟล์ใบ) = สร้างใหม่ 1 ครั้ง (ราว 2–4 นาที) แล้วจำลายไว้ที่ `%USERPROFILE%\.pms-testdb-schema.json`
  - ลองใบใหม่: เขียนไฟล์ใบในโฟลเดอร์ตัวเองแล้วขอล็อก (ได้ฐานตามไฟล์ของตัวเอง) · ห้ามลงคำสั่งด้วยมือ — ของที่ไม่มีไฟล์ถูกสร้างใหม่ทับตอนคนถัดไปขอล็อก
  - ข้อทดสอบ: `node tests/tools/testdb-schema.test.mjs` · พิสูจน์: `node tests/tools/testdb-schema-mutation.mjs`
- **`npm run dev` ใช้ฐาน dev (pms-dev) ไม่ใช่ฐานทดสอบ** — เปิดฐาน dev ให้เอง ลงใบปรับฐานที่ขาด และใส่ข้อมูลตัวอย่างตอนเป็นฐานใหม่ (`scripts/dev-db.mjs`) · บันทึกได้ตามปกติ · รอบตรวจ/ข้อทดสอบห้ามแตะฐาน dev (ชุดทดสอบหยุดเองถ้าชี้ฐาน dev)
- ตัวตรวจของค้าง (`check-test-leftovers`) บอกว่าแถวค้างมาจากเซสชันไหน (เทียบเวลาสร้างแถวกับประวัติผู้ถือล็อก `%USERPROFILE%\.pms-testdb-lock-history.jsonl`) · เซสชันอื่นถือล็อกอยู่ = หยุดบอกว่าใครใช้ ไม่ใช่ตก
- ทำพังเพื่อพิสูจน์ข้อทดสอบ ทำในโฟลเดอร์ของตัวเองเท่านั้น
- ห้ามเขียนเลขพอร์ตหรือ `localhost:<พอร์ต>` ในโค้ดและข้อทดสอบ ใช้ `tests/scenario/sessionPorts.ts` หรือ `scripts/lib/session.mjs`

## 3. ส่งงานให้คนรวมงาน

1. commit งานครบ (`git status` ว่าง)
2. รันรอบตรวจเต็มในโฟลเดอร์ตัวเอง `npm run test:prodbuild` ให้ผ่าน ตก 0
3. commit ไฟล์บันทึกที่รอบตรวจเขียนให้ (`supabase/gate-passed-code.txt` · `supabase/gate-passed-migrations.json`)
4. แจ้งคนรวมงานว่า "ส่งงาน session/<ชื่อ>"

คนรวมงานสั่ง `npm run session:merge -- <ชื่อ>` คำสั่งนี้ไม่ยอม merge เมื่อ:
- commit ล่าสุดของ branch ไม่มีผลรอบตรวจเต็มผ่าน
- ชนกันในไฟล์งาน (ให้เซสชันดึง `wip/integration` ไปแก้ในโฟลเดอร์ตัวเอง แล้วรันรอบตรวจใหม่)
- merge แล้วเลขใบปรับฐานขาดช่วง (ต้อง merge ตามลำดับเลข คำสั่งบอกว่าเลขที่ขาดเป็นของเซสชันไหน)

หลัง merge (บอสสั่ง 27 ต.ค. 69 · คำสั่ง merge บอกเอง):
- **โค้ดหลังรวมตรงกับ commit ที่เซสชันตรวจผ่านทุกไฟล์ (ลายนิ้วมือตรง)** → ใช้ผลเดิม ไม่ต้องรันรอบตรวจซ้ำ push ได้เลย
  (คำสั่ง merge เติมบรรทัดผลของเซสชันลง `supabase/gate-passed-code.txt` ให้เองถ้าขาด)
- **ไม่ตรง** (สาขาหลักมีงานอื่นที่เซสชันนั้นไม่ได้ตรวจด้วย) → รวมงานที่ตรวจผ่านแล้วรออยู่ของทุกเซสชันให้ครบก่อน (คำสั่งบอกรายชื่อ)
  แล้วรันรอบตรวจรวมทีเดียวในโฟลเดอร์หลัก
- ห้ามข้ามรอบตรวจเมื่อลายนิ้วมือไม่ตรง — pre-push และ Vercel ปฏิเสธ commit ที่ไม่มีผลผ่านอยู่แล้ว
- ทางลัดเวลาส่งหลายงาน: ให้เซสชันที่ส่งทีหลังรวมงานของเซสชันแรกเข้า branch ตัวเองก่อนรันรอบตรวจ → รอบตรวจเดียวครอบทั้งสองงาน
  แล้วคนรวมงานรวมเรียงตามลำดับ (ลายนิ้วมือตรง ไม่ต้องรันซ้ำ)
- ข้อทดสอบ: `tests/tools/session-tools.test.mjs` (ส่วน session:merge)

พอร์ตโฟลเดอร์หลัก: `npm run dev` ใช้ 3001/3002 · รอบตรวจเต็มใช้ 3011/3012 (`scripts/lib/ports.json`) — เปิดเว็บดูอยู่ระหว่างรอบตรวจได้ ไม่ต้องปิด
ผล build ของรอบตรวจ/ชุดทดสอบอยู่ `apps/*/.next-test` ไม่ใช่ `.next` ที่ `npm run dev` ใช้ (บอสสั่ง 28 ต.ค. 69 · เดิม build ทับ dev จนพังทั้งคู่) — ตั้งที่ `scripts/test-prodbuild.mjs` · ข้อทดสอบ `tests/tools/dev-build-separate.test.mjs`
รอบตรวจเต็มเจอข้อตก → รันซ้ำเฉพาะไฟล์ที่ตกบน commit/เซิร์ฟเวอร์เดิมก่อนปิดรอบ ผ่าน = นับไม่นิ่ง (จดลงตัวนับ) ไม่ต้องรันใหม่ทั้งรอบ · ยังตก/ครบเกณฑ์ 3 = ตกจริง (บอสสั่ง 28 ต.ค. 69 · `scripts/lib/gateRerun.mjs`) · ตัวตรวจกับดัก ∥ ข้อทดสอบหน่วย ∥ build และช่วง tools (`*-tool.spec.ts` ห้ามใช้ฐานทดสอบ/เว็บของรอบตรวจ) ∥ chromium รันพร้อมกัน · เวลาแต่ละช่วงอยู่ `test-results/gate-timing.json` (`PMS_GATE_PARALLEL=0` = เรียงแบบเดิม)

## 4. ปิดเซสชัน (คนรวมงานสั่งจากโฟลเดอร์หลัก)

```
npm run session:close -- <ชื่อ>
```

ถอดทางลัดทุกตัวก่อน แล้วจึงลบโฟลเดอร์ ลบ branch และคืนช่องพอร์ต
งานยังไม่ merge หรือมีไฟล์ค้าง = ไม่ปิด (ตั้งใจทิ้งงาน: `--ทิ้งงาน`)
**ห้ามลบโฟลเดอร์เซสชันด้วยมือ** เพราะ 22 ต.ค. 69 การลบแบบเดินตามทางลัดเคยทำไฟล์ของโฟลเดอร์หลักหาย

## ตัวกันขึ้นเว็บจริง

| ชั้น | กันอะไร | ข้ามได้ไหม |
|---|---|---|
| git pre-push ในเครื่อง | push ขึ้น monorepo ได้เมื่อ commit ผ่านรอบตรวจเต็ม และฐานจริงมีใบปรับฐานครบ | ข้ามได้ด้วย `--no-verify` (ห้ามใช้) |
| ด่าน Vercel | branch monorepo ไม่ build commit ที่ไม่ผ่านรอบตรวจเต็ม | ข้ามไม่ได้ (Vercel เป็นคนรัน) |

ผลรอบตรวจคือ "ลายนิ้วมือโค้ด" ในไฟล์ `supabase/gate-passed-code.txt` ที่ commit ไว้
แก้ไฟล์ใดก็ตามหลังรอบตรวจผ่าน = ลายนิ้วมือเปลี่ยน = ต้องรันรอบตรวจใหม่
commit เปล่าเพื่อขึ้นเว็บ (`deploy: …`) ไม่เปลี่ยนลายนิ้วมือ

**ด่าน Vercel ไม่ตรวจใบปรับฐานบนฐานจริง** เพราะ:
- ด่านรันก่อนติดตั้งโปรแกรมเสริม และไม่มีค่าเชื่อมต่อฐานข้อมูลโดยตรง
- ตารางประวัติใบปรับฐานไม่ได้เปิดให้อ่านผ่านช่องทางที่แอปใช้
- ถ้าจะให้ตรวจได้ ต้องเพิ่มใบปรับฐานที่เปิดคำสั่งอ่านเลขใบ และให้ขั้น build ถือกุญแจฐานจริง ซึ่งเพิ่มความเสี่ยงมากกว่าที่ได้

การตรวจใบปรับฐานจึงอยู่ที่ตัวกันในเครื่อง ซึ่งถามฐานจริงทุกครั้ง

## ตัวนับข้อไม่นิ่ง (บอสสั่ง 26 ต.ค. 69)

- ทุกรอบตรวจเต็มจดข้อที่ "ตกแล้วผ่านตอนรันซ้ำ" ลงไฟล์เดียว `tests/flaky-log.txt` (บรรทัด `ไม่นิ่ง | วันที่ | รอบ | ไฟล์ › ชื่อข้อ`)
- ข้อไหนไม่นิ่งครบ 3 ครั้งโดยยังไม่มีบรรทัด `ต้นเหตุ | วันที่ | ไฟล์ › ชื่อข้อ | ข้อความ` → รอบตรวจขึ้น "⛔ ต้องหาต้นเหตุ" และไม่บันทึกผลผ่าน = ขึ้นเว็บไม่ได้
- หาต้นเหตุได้แล้ว: เขียนบรรทัด `ต้นเหตุ` (ห้ามแก้ด้วยการเพิ่มเวลารอ) แล้วรันรอบตรวจใหม่
- ไฟล์นี้ไม่นับในลายนิ้วมือโค้ด และ git รวมบรรทัดจากหลายเซสชันเอง (merge=union) · commit ไฟล์นี้พร้อมงานทุกครั้ง
- ตัวนับ: `scripts/lib/flakyLog.mjs` · ข้อทดสอบ: `tests/tools/flaky-log.test.mjs`
